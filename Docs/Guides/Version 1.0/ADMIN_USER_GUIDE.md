# SmartFlow Beauty: руководство администратора салона

Версия документа: 1.0  
Для кого: администраторы, управляющие записями через Admin Bot

## 1. Назначение и границы ответственности

Admin Bot используется для обработки заявок, просмотра записей, управления клиентами, мастерами, услугами, локациями и доступной конфигурацией. Он не является финансовой системой: цены, валюта и платежи не хранятся.

Обычный администратор работает через Telegram. Править структуру Google Sheets, Apps Script, webhook, токены и триггеры должен только технический владелец.

## 2. Доступ

Admin Bot разрешает работу только Telegram ID из `AdminTelegramIds`. Если отображается «Доступ запрещён», попросите действующего администратора добавить ваш числовой ID через Settings → Configuration → Administrators.

Не передавайте доступ к личному Telegram-аккаунту. При увольнении сотрудника удалите его ID сразу.

### Работа администратора с iPhone

Для Admin Bot нужен Telegram, но Google Account не требуется, пока вы работаете только через бот. Для просмотра или редактирования рабочей таблицы и календарей нужен именно тот Google-аккаунт, которому владелец выдал доступ. Apple ID/iCloud не заменяет Google Account.

Рекомендуемая настройка iPhone:

1. Установите актуальные Telegram, Google Sheets и Google Calendar из App Store.
2. Войдите в Sheets и Calendar под рабочим Google-аккаунтом. Если аккаунтов несколько, проверяйте адрес под аватаром в каждом приложении отдельно.
3. Откройте приглашение к таблице и календарям. Наличие Telegram ID в `AdminTelegramIds` не предоставляет права на Google-ресурсы автоматически.
4. В Google Calendar откройте боковое меню и включите отображение календарей всех мастеров, которые вам нужны.
5. Откройте «Настройки → Приложения → Telegram → Уведомления» и включите уведомления, звук и баннеры. Добавьте Telegram в разрешённые приложения используемого режима «Фокусирование» либо временно отключите этот режим для проверки.
6. Разрешите Telegram мобильные данные, если администратор работает без Wi-Fi.

Развёртывание, `clasp push`, изменение Web App и управление Apps Script-триггерами выполняет технический владелец с компьютера. Не пытайтесь чинить production-развёртывание только с iPhone.

## 3. Главное меню

Главные разделы:

- «Записи» — оперативный просмотр расписания;
- «Клиенты» — профили, история и конфликты;
- «Настройки» — мастера, услуги, локации и конфигурация.

Кнопка «Назад» возвращает на предыдущий уровень, «Главное меню» сбрасывает незавершённый мастер ввода и возвращает к началу.

## 4. Обработка новой заявки

Когда клиент отправляет заявку, все администраторы из `AdminTelegramIds` и дополнительные активные получатели из `RequestRecipients` получают сообщение с вариантами. Повторяющиеся Telegram ID автоматически объединяются.

1. Проверьте имя, телефон, услугу, мастера, локацию, комментарий и предложенные даты.
2. Нажмите подтверждение только одного подходящего варианта.
3. После успешного подтверждения создаются запись в Appointments и событие Google Calendar.
4. Клиент получает подтверждение.
5. Если ни один вариант не подходит, отклоните заявку и при необходимости свяжитесь с клиентом.

Не нажимайте старые inline-кнопки повторно. Защита от дублей существует, но операцию всегда следует проверять по ответу бота и разделу «Записи».

## 5. Раздел «Записи»

Доступные представления:

- сегодня;
- завтра;
- следующий рабочий день мастера;
- по мастеру;
- по выбранной дате.

Экраны читают текущие Appointments и Google Calendar напрямую. После создания, переноса, отмены или ручного изменения Calendar-события данные должны отображаться без ожидания cache-триггера.

Карточка может показывать клиента, телефон, услугу, мастера, локацию, комментарий и статус подтверждения клиентом.

### Ручные Calendar-события

Ручное событие остаётся событием Calendar и используется как занятый слот и запись в Admin Bot. Для максимально полной карточки используйте описание:

```text
Клиент: Имя
Телефон: 0770000000
Услуга: Название услуги
Мастер: Имя мастера
Локация: Название филиала
Комментарий: текст или -
```

Событие должно находиться в календаре нужного мастера. Занятость одного мастера не блокирует других. Ручные события нельзя переносить клиентским сценарием; изменяйте их в Google Calendar.

После завершения ручного события с известным телефоном часовая синхронизация может добавить визит в историю и CustomerProfiles.

## 6. Клиенты

### Список и профиль

Список CustomerProfiles поддерживает пагинацию. Размер страницы задаётся общей настройкой `PaginationPageSize`. Профиль можно найти по телефону, создать вручную, изменить или удалить.

`Customers` — динамические данные взаимодействия и Telegram. `CustomerProfiles` — накопленный профиль клиента после завершённого визита либо ручного ввода администратором.

### История визитов

История выводится страницами и строится из CustomerVisitHistory. Завершённые подтверждённые записи добавляются часовым `syncCompletedCustomerVisitsTrigger`. Повторный запуск не должен создавать дубль по Calendar event ID.

### Индивидуальные настройки услуги

Для клиента можно настроить индивидуальную длительность услуги. Финансовых полей нет.

### Конфликты

Используйте конфликты для ограничений клиента на определённые интервалы. Создавайте, просматривайте и удаляйте их только при понятной бизнес-причине.

## 7. Мастера

Раздел позволяет:

- добавить мастера;
- посмотреть список;
- изменить данные;
- включить или отключить;
- настроить недельный график;
- добавить или удалить исключения графика.

При создании Telegram ID мастера не требуется. Его можно добавить позже при редактировании.

Каждый мастер должен быть связан с локацией и правильным Google Calendar. Если несколько мастеров используют один календарь, описание ручного события должно однозначно содержать имя мастера; безопаснее использовать отдельный календарь на мастера.

Отключение мастера скрывает его из новых клиентских сценариев, но не должно использоваться как способ отменить существующие записи.

## 8. График и исключения

Недельный ProviderSchedule определяет обычные рабочие дни и часы. ProviderScheduleOverrides задаёт исключения на конкретную дату: изменённое время или нерабочий день.

Перед сохранением проверяйте формат времени и то, что конец позже начала. Изменение часов по умолчанию влияет на новые графики и fallback, но не переписывает уже сохранённые расписания.

Если слот не показывается, сначала проверьте график, исключение, длительность услуги и Calendar мастера.

## 9. Услуги

Можно добавить услугу, посмотреть список, изменить, включить или отключить. Услуга хранит название, локацию, длительность и активность. После включения или отключения бот автоматически возвращает меню услуг.

Отключённая услуга недоступна для новой записи. Существующие подтверждённые записи не следует удалять ручным отключением услуги.

## 10. Локации

Можно посмотреть, добавить, изменить, включить и отключить локацию. Контактные поля могут включать адрес, телефоны, часы работы, Telegram, Instagram, сайт и Google Maps. Эти данные показываются клиенту в «Контактах».

Перед отключением проверьте будущие записи и мастеров, привязанных к локации.

## 11. Configuration

Через Telegram разрешено менять только allowlisted параметры:

- язык `uk`, `ru`, `en`;
- список администраторов;
- напоминание за день;
- горизонт онлайн-записи от 1 до 365;
- размер страницы от 1 до 10;
- рабочие часы по умолчанию.

Системные токены, AppsScriptUrl, TimeZone и Calendar ID не меняются через UI.

### Администраторы

Используйте отдельные кнопки «Список», «Добавить» и «Удалить». Вводите один числовой Telegram ID. Нельзя удалить самого себя. После изменения бот сохраняет полный список через запятую.

Каждый администратор из этого списка автоматически получает новые заявки, уведомления об отмене и переносе, а также подтверждения клиентов. Нажатие Start само по себе не выдаёт права и не включает уведомления: ID должен присутствовать в списке администраторов.

Если заявку одновременно получили несколько администраторов, обработать её сможет только первый. Подтверждение или отклонение из устаревшей карточки не должно изменить уже обработанную заявку.

### Напоминание

Отключение `ReminderDayBefore` останавливает выбор и отправку 24-часовых напоминаний, но не удаляет записи.

### Горизонт записи

Определяет, на сколько дней вперёд клиент и администратор могут выбирать даты. После удаления CalendarCache отдельного горизонта кеша нет.

## 12. Перенос и отмена клиентом

Клиент управляет подтверждённой bot-записью из «Мои записи». Перенос обновляет Appointments и Calendar, очищает поля старого напоминания и подтверждения. Администратор получает уведомление.

Отмена меняет статус и удаляет связанное Calendar-событие. Клиент получает информационную карточку без повторных кнопок.

Ручное Calendar-событие изменяется администратором непосредственно в Calendar.

## 13. Ежедневная операционная проверка

В начале смены:

1. Откройте записи на сегодня.
2. Сравните первые записи с Google Calendar.
3. Проверьте неподтверждённые клиентами визиты.
4. Убедитесь, что новые заявки доходят ответственным администраторам.
5. Проверьте исключения графика при болезни или выходном мастера.

В конце смены:

1. Проверьте записи на завтра.
2. Убедитесь, что отмены и переносы отражены в Calendar.
3. Не удаляйте строки Appointments или AuditLog вручную.

## 14. Если что-то перестало работать

### Шаг 1. Не усугублять

Не меняйте токены, заголовки таблиц, Script ID, deployment, статусы и триггеры наугад. Зафиксируйте время, действие, текст ошибки и скриншот.

### Шаг 2. Проверить масштаб

- не работает только одна кнопка или оба бота;
- проблема у одного пользователя или у всех;
- Calendar работает отдельно;
- новые сообщения приходят, но данные неверны;
- была ли перед проблемой правка таблицы, deployment или Calendar.

### Бот не отвечает всем

Передайте техническому владельцу название бота и время. Он должен проверить webhook, deployment и `DOPOST_ERROR` в AuditLog. Обычный администратор может попробовать `/start`, но не должен переустанавливать webhook без доступа к установке.

### «Доступ запрещён» у администратора

Действующий администратор проверяет список в Configuration. Если доступ потеряли все, технический владелец исправляет `AdminTelegramIds` в Settings как текст и перезапускает диалог.

### Новые заявки не приходят

Проверьте, что ID администратора присутствует в Configuration и клиент получил финальное сообщение. Технический владелец проверяет объединённый список администраторов и `RequestRecipients`, Admin webhook, AuditLog и наличие созданных Requests/RequestOptions.

### Подтверждение не создаёт запись

Не нажимайте много раз. Проверьте Appointments и Calendar. Передайте request ID/время техническому владельцу. Он проверит ошибки Calendar, права и callback в AuditLog.

### Admin Bot показывает неверное расписание

Сравните запись Appointments и событие Calendar. После удаления CalendarCache ждать триггер не нужно. Проверьте правильный Calendar ID мастера, часовой пояс и структурированное описание ручного события.

### Нет доступных слотов

Проверьте активность локации/услуги/мастера, ProviderSchedule, overrides, длительность услуги, события Calendar и часовой пояс. Не удаляйте Calendar-события, не связавшись с клиентами.

### Напоминание не пришло

Технический владелец проверяет `ReminderDayBefore`, installable trigger, время 08:00–23:00, Telegram ID клиента и поля напоминания. Уже отправленное напоминание повторно не отправляется, кроме корректного переноса записи.

Если проблема только на iPhone одного пользователя, сначала откройте чат Telegram и проверьте, есть ли сообщение внутри. Затем проверьте уведомления Telegram, «Фокусирование», сводку уведомлений и мобильные данные. Если сообщения нет и у других пользователей, передавайте проблему техническому владельцу.

### Статус подтверждения обновился с задержкой

Сначала обновите экран «Записи». Если callback дошёл, Appointments должен содержать время подтверждения. Синхронизация справочников не должна использоваться для исправления callback.

### История визитов не обновилась

Проверьте, что визит завершён, запись confirmed, есть Calendar event ID и работает `syncCompletedCustomerVisitsTrigger`. Для ручного события нужен валидный телефон в описании.

### После обновления работает старая версия

Технический владелец должен проверить, что после `clasp push` обновлён production Web App deployment. URL webhook должен указывать на актуальный `/exec`.

## 15. Что технический владелец проверяет при аварии

1. Apps Script Executions и AuditLog за точное время.
2. `getClientWebhookInfo()` и `getAdminWebhookInfo()`.
3. Токены и `AppsScriptUrl` без вывода секретов посторонним.
4. Production deployment и права «execute as»/«Anyone».
5. Installable triggers и отсутствие дублей.
6. Доступ аккаунта deployment к таблице и календарям.
7. Имена листов и заголовков по DATABASE_SCHEMA.
8. Квоты Apps Script, UrlFetch и Calendar.

После исправления выполняется короткая регрессия: `/start` обоих ботов, тестовая заявка, подтверждение, просмотр записи и проверка Calendar.

## 16. Резервное восстановление

Перед крупным обновлением создайте копию Google-таблицы и зафиксируйте рабочую версию deployment. При сбое не откатывайте только код, если миграция уже изменила схему: сначала оцените совместимость данных.

Никогда не используйте случайный старый `.clasp.json` — он может загрузить код в чужой Script ID.

## 17. Что сообщить в техническую поддержку

- салон и имя бота;
- дата, время и часовой пояс;
- Telegram ID администратора, если проблема доступа;
- раздел и последовательность действий;
- точный текст ошибки;
- request/appointment ID, если он виден в технических данных;
- скриншоты без токенов и лишних персональных данных;
- были ли перед этим `clasp push`, deployment, миграция или ручная правка Sheets.

Не отправляйте токены в обычный чат поддержки. Для ротации используйте защищённый канал владельца.
