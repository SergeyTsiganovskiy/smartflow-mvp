# Аудит SmartFlow Beauty Demo Real.xlsx

Дата аудита: 2026-07-14  
Режим: только чтение; исходный XLSX не изменялся.

## Итог

В книге найдено 22 листа. Текущий runtime объявляет 20 листов. Основные рабочие таблицы соответствуют коду, однако обнаружены четыре группы технического долга:

1. `AuditLog` не имеет корректной строки заголовков;
2. листы `ProviderServices` и `Notifications` полностью не используются текущим кодом;
3. `Messages` содержит 22 пустых столбца E:Z;
4. `UserSessions` содержит 40 legacy-столбцов, хотя новые записи хранят состояние в `session_data`.

Удалять что-либо вручную до миграции не рекомендуется.

## Критическая проблема

### AuditLog

Ожидаемая схема: `timestamp`, `action`, `details`.

В реальной книге первая строка содержит событие `DOPOST_ADMIN_DEBUG` и его payload, то есть является строкой лога, а не заголовком. Функция `addAuditLog()` продолжает добавлять три значения позиционно, поэтому новые записи создаются, но схема листа повреждена, первая запись воспринимается инструментами как заголовок, а дальнейший анализ ненадёжен.

Рекомендация: отдельная repeat-safe миграция должна вставить правильную строку заголовков, если A1:C1 не равны ожидаемой схеме. Существующие события нельзя удалять или переставлять без резервной копии.

## Безопасные кандидаты на удаление

### Лист ProviderServices

В книге есть три колонки: `provider_id`, `service_id`, `active`. Лист отсутствует в `SHEET_NAMES`, код не читает его по имени и не использует эти поля. Текущая модель выбирает мастеров по локации, а не по отдельной связи мастер-услуга.

Вывод: лист не используется и может быть удалён миграцией, если бизнес не планирует ограничивать услуги конкретными мастерами.

### Лист Notifications

Колонки: `notification_id`, `appointment_id`, `type`, `send_at`, `sent_at`, `status`. Все строки пусты. Лист отсутствует в `SHEET_NAMES`. Текущие 24-часовые напоминания используют поля Appointments `reminder_24h_sent_at`, `customer_confirmed` и `customer_confirmed_at`.

Вывод: лист безопасный кандидат на удаление.

### Пустые столбцы Messages

Используются только A:D: `key`, `uk`, `ru`, `en`. Столбцы E:Z имеют пустые заголовки и полностью пусты.

Вывод: E:Z можно удалить. Они расширяют used range, замедляют чтение/рендер и создают риск случайной записи в безымянную колонку.

## UserSessions

Из 43 колонок runtime обязательно использует только:

- `telegram_id`;
- `session_data`;
- `updated_at`.

Все setters записывают состояние в JSON `session_data`. `getUserSession()` пока сначала читает legacy-колонки, а затем накладывает JSON поверх них для совместимости со старыми установками.

В реальной книге три активные строки имеют `session_data`; legacy-поля в них пусты. Кандидаты на удаление:

`location_id`, `service_id`, `provider_id`, `reschedule_appointment_id`, `pending_calendar_event_id`, `edit_provider_id`, `schedule_provider_id`, `override_provider_id`, `override_reason_key`, `edit_provider_field`, `previous_menu`, `schedule_day_code`, `edit_provider_new_value`, `provider_name`, `provider_location_id`, `provider_phone`, `provider_telegram_id`, `option_count`, `current_option_date`, `current_option_time`, `option1_date`, `option1_time`, `option2_date`, `option2_time`, `option3_date`, `option3_time`, `reschedule_date`, `reschedule_time`, `customer_name`, `customer_phone`, `customer_note`, `customer_id`, `override_date`, `override_start_time`, `override_end_time`, `service_name`, `service_location_id`, `service_duration_min`, `service_duration_max`, `state`.

Перед удалением нужно:

1. изменить `getUserSession()`, чтобы он больше не читал legacy-колонки;
2. добавить миграцию, которая переносит любое непустое legacy-значение в `session_data`, не перезаписывая существующий JSON;
3. только затем удалить legacy-колонки справа налево;
4. проверить незавершённые клиентские и административные мастера ввода.

`pending_calendar_event_id` особенно устарел: прямой перенос Calendar-событий уже удалён.

## Поля, которые выглядят пустыми, но используются

Их удалять нельзя только на основании пустоты в тестовой книге:

- CustomerProfiles: `sales_hint`, `note` — отображаются и редактируются Admin Bot;
- Customers: `last_visit_at`, `status`, `notes` — команды создания/обновления используют схему;
- CustomerServiceSettings: `notes` — читается в карточке и записывается командами;
- CustomerConflicts: `notes` — часть текущей схемы создания;
- Providers: `telegram_id` — необязателен при создании, но редактируется позже;
- Appointments: поля напоминания и подтверждения — критичны для повторного напоминания после переноса;
- CustomerVisitHistory: денормализованные имена нужны для сохранения исторической карточки, даже если сущность позже переименована.

## Условные кандидаты

### Settings.comment

Третий столбец полностью пуст, а `getSettings()` читает только первые два. Его можно удалить, но комментарии полезны как человеческая документация системных настроек. Рекомендация: оставить и заполнить безопасными описаниями либо удалить из чистого production-шаблона.

### ProviderSchedule.notes

Код возвращает расписание без `notes`; в реальной книге заполнены три значения. Поле описано в схеме как внутреннее примечание. Удалять только после решения, нужны ли эти заметки администратору в будущем.

### RequestRecipients

Для доставки runtime фактически проверяет `telegram_id`, `receive_new_requests` и `active`. Поля `recipient_id`, `name`, `provider_id`, `role` сейчас не участвуют в фильтрации, но полезны как административные метаданные и задел для адресной маршрутизации. Пока оставить.

## Лишние строки и форматирование

Несколько листов имеют used range около 1000 строк, хотя фактических записей значительно меньше: CustomerProfiles, UserSessions, CustomerServiceSettings, Locations и Customers. Это похоже на форматирование или когда-то очищенные значения в нижних строках.

Рекомендация: миграция не должна удалять строки по `getLastRow()` вслепую. Сначала определить последнюю строку с реальным ключом в первой колонке, затем очищать только полностью пустой хвост. Это оптимизация размера файла, не изменение схемы.
